# この記事について

TiDB では v8.5.0 から [Index Advisor](https://docs.pingcap.com/tidb/stable/index-advisor/) という機能が利用できるようになりました。この機能を使うことで、対象クエリに対して適切なインデックスを見つけやすくなります。Index Advisor は特定クエリだけでなく、過去一定期間のクエリの実行状況から、実行頻度の高いクエリに対するインデックスを推薦することも可能であるため、日常的なクエリチューニングに利用することも出来ます。

この記事では、Index Advisor の使い方などを紹介し、推薦されたインデックスが本当に適切かどうかを実際に検証して、Index Advisor の信頼性を確かめてみます。

この記事を通じて、Index Advisor がどのようにしてインデックスを推薦しているのか、その推薦されたインデックスは信頼できるのかどうかを確かめて、本番運用中のシステムに対して、どのように導入すべきかまでを解説し、読者の皆さんのインデックス戦略のお役に立てることを目指します。

Index Advisor のようなインデックスを推薦する機能は TiDB 独自というわけではありませんが、本記事の読者は TiDB を知っていることを前提としています。

# Index Advisorとは何か

改めて Index Advisor とは何かを申し上げると、過去のワークロードや特定のクエリに対して、適切なインデックスを推薦する機能です。このセクションでは、Index Advisor の基本的な使い方から始め、Index Advisor はどのように適切なインデックスを決定しているのかを深掘りします。

##  TiDB Index Advisorの基本的な使い方

Index Advisor には専用のUIはなく、通常のMySQLクライアントからSQLコマンドとして以下を実行します。

```sql
RECOMMEND INDEX RUN [ FOR <SQL> ] [<Options>]
```

オプションの内容は後述するとして、早速使ってみましょう。ここでは、ドキュメントに記載されている例と同じ例を用いて説明します。

https://docs.pingcap.com/tidb/stable/index-advisor/

### クエリ単体を対象とする場合

以下のテーブルを用意します。

```sql
CREATE TABLE t (a INT, b INT, c INT);
```

このテーブルに対して、`SELECT a, b FROM t WHERE a = 1 AND b = 1` というクエリのインデックスを推薦してもらいます。

```sql
tidb:4000 > RECOMMEND INDEX RUN for "SELECT a, b FROM t WHERE a = 1 AND b = 1"\G
*************************** 1. row ***************************
          database: test
             table: t
        index_name: idx_a_b
     index_columns: a,b
        index_size: 0
            reason: Column [a b] appear in Equal or Range Predicate clause(s) in query: select `a` , `b` from `test` . `t` where `a` = ? and `b` = ?
top_impacted_query: [{"Query":"SELECT `a`,`b` FROM `test`.`t` WHERE `a` = 1 AND `b` = 1","Improvement":0.999994}]
1 row in set (0.04 sec)
```

結果の詳細は後で見ていきますが、ここでは `index_columns` と `reason` に注目してください。ドキュメントと同じ結果となりましたが、このクエリに対して、 `a` 列と `b` 列を組み合わせたインデックスが推薦されました。

では `SELECT a, b FROM t WHERE a > 1 AND b = 1` の場合はどうでしょうか。先ほどのクエリでは `a=1` だった条件を `a>1` に変えました。

```sql
tidb:4000 > RECOMMEND INDEX RUN for "SELECT a, b FROM t WHERE a > 1 AND b = 1"\G
*************************** 1. row ***************************
          database: test
             table: t
        index_name: idx_b_a
     index_columns: b,a
        index_size: 0
            reason: Column [b a] appear in Equal or Range Predicate clause(s) in query: select `a` , `b` from `test` . `t` where `a` > ? and `b` = ?
top_impacted_query: [{"Query":"SELECT `a`,`b` FROM `test`.`t` WHERE `a` \u003e 1 AND `b` = 1","Improvement":0.998129}]
1 row in set (0.03 sec)
```

今回は、 `b` 列、`a` 列の順番での複合インデックスが推薦されました。`b` 列の条件が等価条件であるため、 `b` 列から照合したほうが絞り込みが効率的になります。

### ワークロードを対象とする場合

テーブルを２つ用意します。

```sql
CREATE TABLE t1 (a INT, b INT, c INT, d INT);
CREATE TABLE t2 (a INT, b INT, c INT, d INT);
```

いくつかクエリを実行します。

```sql
SELECT a, b FROM t1 WHERE a=1 AND b<=5;
SELECT d FROM t1 ORDER BY d LIMIT 10;
SELECT * FROM t1, t2 WHERE t1.a=1 AND t1.d=t2.d;
```

非常に小さいですが、これらのワークロードを対象にまとめてインデックスの推薦を受けてみます。構文は先ほどのクエリから `FOR <SQL>` を除くだけです。

```sql
tidb:4000 > RECOMMEND INDEX RUN;
+----------+-------+------------+---------------+------------+-----------------------------------------------------------------------------------------------------------------------------------------------------------------------+---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
| database | table | index_name | index_columns | index_size | reason                                                                                                                                                                | top_impacted_query                                                                                                                                                                                                              |
+----------+-------+------------+---------------+------------+-----------------------------------------------------------------------------------------------------------------------------------------------------------------------+---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
| test     | t1    | idx_a_b    | a,b           | 0          | Column [a b] appear in Equal or Range Predicate clause(s) in query: select `a` , `b` from `test` . `t1` where `a` = ? and `b` <= ?                                    | [{"Query":"SELECT `a`,`b` FROM `test`.`t1` WHERE `a` = 1 AND `b` \u003c= 5","Improvement":0.998214},{"Query":"SELECT * FROM (`test`.`t1`) JOIN `test`.`t2` WHERE `t1`.`a` = 1 AND `t1`.`d` = `t2`.`d`","Improvement":0.337273}] |
| test     | t1    | idx_d      | d             | 0          | Column [d] appear in Equal or Range Predicate clause(s) in query: select `d` from `test` . `t1` order by `d` limit ?                                                  | [{"Query":"SELECT `d` FROM `test`.`t1` ORDER BY `d` LIMIT 10","Improvement":0.999669}]                                                                                                                                          |
| test     | t2    | idx_d      | d             | 0          | Column [d] appear in Equal or Range Predicate clause(s) in query: select * from ( `test` . `t1` ) join `test` . `t2` where `t1` . `a` = ? and `t1` . `d` = `t2` . `d` | [{"Query":"SELECT * FROM (`test`.`t1`) JOIN `test`.`t2` WHERE `t1`.`a` = 1 AND `t1`.`d` = `t2`.`d`","Improvement":0.639393}]                                                                                                    |
+----------+-------+------------+---------------+------------+-----------------------------------------------------------------------------------------------------------------------------------------------------------------------+---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
3 rows in set (0.19 sec)
```

ワークロードを対象とする場合、実行頻度の高いクエリが上位に来るため、実行されているクエリを個別にトラッキングする必要はありません。推薦結果はご覧のとおりですが、このようにまとめてインデックスの推薦を受けることができるので、日常的なクエリチューニングとして便利に使えます。

Index Advisor の基本的な使い方は以上です。
## Improvement値の意味

ところで、これまで見てきた推薦結果の中に、`Improvement` という項目があったことに気づきましたか？ `top_impacted_query` 列にあります。

```sql
tidb:4000 > RECOMMEND INDEX RUN for "SELECT a, b FROM t WHERE a = 1 AND b = 1"\G
*************************** 1. row ***************************
          database: test
             table: t
        index_name: idx_a_b
     index_columns: a,b
        index_size: 0
            reason: Column [a b] appear in Equal or Range Predicate clause(s) in query: select `a` , `b` from `test` . `t` where `a` = ? and `b` = ?
top_impacted_query: [{"Query":"SELECT `a`,`b` FROM `test`.`t` WHERE `a` = 1 AND `b` = 1","Improvement":0.999994}]
1 row in set (0.04 sec)
```

この `Improvement` とはどのような意味でしょうか？結論から言うと、この `Improvement` とはオプティマイザが計算するコストがどの程度の割合で改善するのかを示したものです。上記の推薦結果では、`"Improvement":0.999994` となっていました ので、実際にインデックスを追加して確認してみましょう[^1]。

```sql
tidb:4000 > EXPLAIN FORMAT='verbose' SELECT a, b FROM t WHERE a = 1 AND b = 1;
+-------------------------+----------+------------+-----------+---------------+----------------------------------+
| id                      | estRows  | estCost    | task      | access object | operator info                    |
+-------------------------+----------+------------+-----------+---------------+----------------------------------+
| TableReader_7           | 0.01     | 392133.42  | root      |               | data:Selection_6                 |
| └─Selection_6           | 0.01     | 5882000.00 | cop[tikv] |               | eq(test.t.a, 1), eq(test.t.b, 1) |
|   └─TableFullScan_5     | 10000.00 | 4884000.00 | cop[tikv] | table:t       | keep order:false, stats:pseudo   |
+-------------------------+----------+------------+-----------+---------------+----------------------------------+
3 rows in set (0.00 sec)

tidb:4000 >  ALTER TABLE t ADD INDEX idx_a_b (a, b);
Query OK, 0 rows affected (0.13 sec)

tidb:4000 > EXPLAIN FORMAT='verbose' SELECT a, b FROM t WHERE a = 1 AND b = 1;
+------------------------+---------+---------+-----------+------------------------------+-------------------------------------------------+
| id                     | estRows | estCost | task      | access object                | operator info                                   |
+------------------------+---------+---------+-----------+------------------------------+-------------------------------------------------+
| IndexReader_6          | 0.10    | 2.20    | root      |                              | index:IndexRangeScan_5                          |
| └─IndexRangeScan_5     | 0.10    | 20.35   | cop[tikv] | table:t, index:idx_a_b(a, b) | range:[1 1,1 1], keep order:false, stats:pseudo |
+------------------------+---------+---------+-----------+------------------------------+-------------------------------------------------+
2 rows in set, 1 warning (0.00 sec)
```

インデックスの追加により、`estCost`が `392133.42` から `2.20` へ改善しました。これを計算してみると、`Improvement`と同じ数値になることがわかります。
```sql
tidb:4000 > SELECT (392133.42-2.20)/392133.42;
+----------------------------+
| (392133.42-2.20)/392133.42 |
+----------------------------+
|                   0.999994 |
+----------------------------+
1 row in set (0.00 sec)
```

このことから、Index Advisor が示す `Improvement` とは、コストがどの程度改善されるかを示したものであることがわかります。なお、ここで行った検証は実際にインデックスを追加せずに、後述する"What-If 分析"でできます。

##  Index Advisorの内部ロジック

Index Advisor はどのようにして適切なインデックスを見出しているのでしょうか？[ドキュメントには以下のように](https://docs.pingcap.com/tidb/stable/index-advisor/#:~:text=The%20Index%20Advisor%20analyzes,executing%20queries%20without%20them.)説明されています。

>The Index Advisor analyzes queries to identify indexable columns from clauses such as `WHERE`, `GROUP BY`, and `ORDER BY`. Then, it generates index candidates and estimates their performance benefits using hypothetical indexes. TiDB uses a genetic search algorithm to select the optimal set of indexes starting with single-column indexes and iteratively exploring multi-column indexes, leveraging a "What-If" analysis to evaluate potential indexes based on their impact on optimizer plan costs. The advisor recommends indexes when they reduce the overall cost compared to executing queries without them.

引用部分では最適なインデックスを見つけるために「遺伝的アルゴリズム（a genetic search algorithm）」を使っていると書かれていますが、[Index Advisor の実装ソースコード](https://github.com/pingcap/tidb/blob/release-8.5-20260724-v8.5.7/pkg/planner/indexadvisor/algorithm.go#L26-L33)を見ると、このアルゴリズムについてもう少し詳しく述べられています。

```go
/*
	This algorithm resembles the index selection algorithm published in 1997 by Chaudhuri
	and Narasayya. Details can be found in the original paper:
	Surajit Chaudhuri, Vivek R. Narasayya: An Efficient Cost-Driven Index Selection
	Tool for Microsoft Query Server. VLDB 1997: 146-155
	This implementation is the Golang version of
	https://github.com/hyrise/index_selection_evaluation/blob/refactoring/selection/algorithms/auto_admin_algorithm.py.
*/
```

このソースコードに基づくと、Index Advisor の元ネタとなっているアルゴリズムは以下の論文です。
- https://www.vldb.org/conf/1997/P146.PDF

また、実装の元ネタとしては、以下の論文で書かれているインデックス選出アルゴリズムのうちの１つである AutoAdmin アルゴリズムを実装したPythonスクリプトであることがわかります。
-  https://www.vldb.org/pvldb/vol13/p2382-kossmann.pdf

ドキュメントからの引用部分とこれらの論文を参考に AutoAdmin アルゴリズムを大雑把に説明すると、以下のとおりです。

1. 対象クエリを分析し、`WHERE`、`GROUP BY`や`ORDER BY`といったところからカラムを選び、最初は単一のインデックス候補とする。
2. #1 で作成した最初の単一列インデックスを"What-If分析"、つまり実際にこのインデックスを適用したらコストがどう改善されるかを評価して、良い結果のインデックスを残す
3. #2 で得られた良い結果となったインデックス候補の末尾に別の列を追加して再度"What-If分析"をする、というプロセスを繰り返して、最適なインデックスを見つける
4. 候補数が少ない場合は、候補の全集合から、一定個数までのインデックスの組み合わせを列挙する

ここで、複合インデックスの候補をどのように生成しているか、v8.5.7の実装を少し見てみましょう。

[calculateBestIndexes](https://github.com/pingcap/tidb/blob/release-8.5-20260819-v8.5.7/pkg/planner/indexadvisor/algorithm.go#L57-L140) では、単一列インデックスから探索を始め、候補の列数を段階的に増やします。

以下のコードブロックはTiDBのソースコードから一部抜粋しており、日本語コメントは筆者が追加しています

```go
potentialIndexes := s.NewSet[Index]() // each indexable column as a single-column index
// 単一列インデックスを収集する
for _, col := range indexableColSet.ToList() {
	potentialIndexes.Add(NewIndex(col.SchemaName, col.TableName, aa.tempIndexName(col), col.ColumnName))
}
...
currentBestIndexes := s.NewSet[Index]()
// インデックス列を１つずつ増やしながら候補となるインデックスを増やす
for currentMaxIndexWidth := 1; currentMaxIndexWidth <= aa.option.MaxIndexWidth; currentMaxIndexWidth++ {
	// `selectIndexCandidates` で候補インデックスを探索する
	candidates, err := aa.selectIndexCandidates(querySet, potentialIndexes)
...
	currentBestIndexes, err = aa.enumerateCombinations(querySet, candidates, maxIndexes)
...
```

各段階で選ばれたインデックス集合は `currentBestIndexes` に格納され、次の段階の候補は以下のように用意されます。

```go
potentialIndexes = currentBestIndexes
potentialIndexes.Add(aa.createMultiColumnIndexes(indexableColSet, currentBestIndexes).ToList()...)
```

このコードから、次の段階へ引き継ぐのは、選ばれたインデックスと、それらを基に生成した複合インデックスであることがわかります。元の候補をすべて拡張するわけではありません。

また、[createMultiColumnIndexes](https://github.com/pingcap/tidb/blob/release-8.5-20260819-v8.5.7/pkg/planner/indexadvisor/algorithm.go#L333-L354) では、元のインデックスの列順を保ち、その末尾に別の列を追加しています。

```go
cols := append([]Column{}, index.Columns...)
cols = append(cols, column)
```

例えば、単一列インデックス `(a)` が選ばれれば、これを基に `(a, b)` を生成できます。一方、`(a)` が残らず `(b)` だけが選ばれた場合、この処理で生成できるのは `(b, a)` であり、`(a, b)` ではありません。

つまり、この探索ループでは、単一列の段階で選ばれなかったインデックスをプレフィックスとする複合インデックスは生成されません。そのため、単一列では効果が小さくても、複合インデックスにすると有効になる候補を見落とす可能性があります。後半の検証では、この探索方法を踏まえて推薦結果を確認します。

なお、ループの後にはIndex Mergeやカバリングインデックス向けの補助的な候補生成処理もあるため、この制約がすべての探索経路に当てはまるわけではありません。

これを読むと、カラム数が多い場合はどうなるのかという組み合わせ爆発の心配が出てきますが、Index Advisor では、インデックスに含める列数を制限する `max_index_columns` などの設定値によって予防されています。これらのオプションは以下で確認できます[^2]。

```sql
tidb:4000 > RECOMMEND INDEX SHOW;
+-------------------+-------+---------------------------------------------------------+
| option            | value | description                                             |
+-------------------+-------+---------------------------------------------------------+
| max_num_index     | 5     | The maximum number of indexes to recommend for a table. |
| max_index_columns | 3     | The maximum number of columns in an index.              |
| max_num_query     | 1000  | The maximum number of queries to recommend indexes.     |
| timeout           | 30s   | The timeout of Index Advisor.                           |
+-------------------+-------+---------------------------------------------------------+
4 rows in set (0.01 sec)
```

##  Hypothetical IndexによるWhat-If分析

Index Advisor では、候補となるインデックスについて What-If 分析を行い、評価すると説明しました。通常、"What-If 分析"といえば、様々な変数を入れ替えながらリスクアセスメントをする手法のことを指しますが、ここでは、様々なカラムを入れ替えながらインデックスを試していく、というようなイメージが近いでしょう。

TiDBでは"What-If分析"にHypothetical Indexを利用しています。具体的には、以下のようにHint句 `/*+ HYPO_INDEX(...) */` を入れて、実際にインデックスを作成することなく、オプティマイザに対して仮想的に設定したインデックスを含めてコストを計算させます。

それでは早速 Hypothetical Index を試してみます。今回もドキュメントに記載されている例を使います。以下の例では `EXPLAIN` に `FORMAT='verbose'` を指定し、コスト（`estCost`列）を追加で表示しています。

```sql
tidb:4000 > CREATE TABLE t(a INT, b INT, c INT);
Query OK, 0 rows affected (0.06 sec)

tidb:4000 > EXPLAIN FORMAT='verbose' SELECT a, b FROM t WHERE a=1 AND b=1;
+-------------------------+----------+------------+-----------+---------------+----------------------------------+
| id                      | estRows  | estCost    | task      | access object | operator info                    |
+-------------------------+----------+------------+-----------+---------------+----------------------------------+
| TableReader_7           | 0.01     | 392133.42  | root      |               | data:Selection_6                 |
| └─Selection_6           | 0.01     | 5882000.00 | cop[tikv] |               | eq(test.t.a, 1), eq(test.t.b, 1) |
|   └─TableFullScan_5     | 10000.00 | 4884000.00 | cop[tikv] | table:t       | keep order:false, stats:pseudo   |
+-------------------------+----------+------------+-----------+---------------+----------------------------------+
3 rows in set (0.00 sec)

tidb:4000 > EXPLAIN FORMAT='verbose' SELECT /*+ HYPO_INDEX(t, idx_ab, a, b) */ a, b FROM t WHERE a=1 AND b=1;
+------------------------+---------+---------+-----------+-----------------------------+-------------------------------------------------+
| id                     | estRows | estCost | task      | access object               | operator info                                   |
+------------------------+---------+---------+-----------+-----------------------------+-------------------------------------------------+
| IndexReader_6          | 0.10    | 2.20    | root      |                             | index:IndexRangeScan_5                          |
| └─IndexRangeScan_5     | 0.10    | 20.35   | cop[tikv] | table:t, index:idx_ab(a, b) | range:[1 1,1 1], keep order:false, stats:pseudo |
+------------------------+---------+---------+-----------+-----------------------------+-------------------------------------------------+
2 rows in set, 1 warning (0.00 sec)
```

このように、実際にインデックスを作成せずとも、仮想的にインデックスを適用してコストを計算することができました。どうやら `idx_ab` は有効そうです。実際にインデックスを追加して、改めて実行計画を見てみましょう。

```sql
tidb:4000 > ALTER TABLE t ADD INDEX idx_ab(a, b);
Query OK, 0 rows affected (0.13 sec)

tidb:4000 > SHOW INDEX FROM t;

+------------------------+---------+---------+-----------+-----------------------------+-------------------------------------------------+
```

実際にインデックスを作成した場合も `HYPO_INDEX` で評価した結果と同じになりました。今回の推薦結果は適切だったと言えます。

このようにして、`HYPO_INDEX`を使った "What-If 分析"で推薦されたインデックスを検証することができます。

## Prepared Statementなどの制限事項

このように便利に使える Index Advisor ですが、いくつか制限があります。公式ドキュメントでは、以下の３つが挙げられています。

1. Prepared statements はサポートされていません
2. 削除すべきインデックスの推薦は行いません
3. Index Advisor の UI は提供されていません

なお、v8.5.7のIndex Advisor は、`SELECT` クエリのみがサポート対象となります。`UPDATE`や`DELETE`クエリを実行すると、以下のようなエラーメッセージが表示されます。

```sql
tidb:4000 > RECOMMEND INDEX RUN FOR 'DELETE FROM t1 WHERE d IS NULL';

ERROR 1288 (HY000): The target table t1 of the DELETE is not updatable
```

ドキュメントには `UPDATE` や `DELETE` に制限があることを言及していないので、このエラーメッセージが仕様通りかどうかは不明ですが[^3]、現時点では `SELECT` クエリに書き換えてインデックスの推薦を受けるのが良さそうです。

# Index Advisorの推薦を検証する

このセクションでは、Index Advisor の機能をさまざまな状況で使い、Index Advisor の信頼性を高めるために必要な条件、言い換えると、Index Advisorを信頼してもよい前提条件を探ってみたいと思います。

## 検証の進め方

この検証では以下のようにして検証を進めます。

1. ケースを再現するためのデータを準備する
2. Index Advisorに推薦させる
	1. どのようなインデックスを推薦したか
	2. `Improvement`の確認
3. 推薦インデックスのHypothetical IndexでEXPLAINする
	1. `estRows`と`estCost`、選択された`Operator`を確認する
4. 比較対象となる別インデックスもHypothetical IndexでEXPLAINする
	1. `estRows`と`estCost`、選択された`Operator`を確認する
5. 実際にそれぞれのインデックスを作る
6. EXPLAIN ANALYZEで実測する
	1. `EXPLAIN ANALYZE`の実行時間の確認
	2. `scan details`や`execution info`の確認
7. Advisorの判断と実測結果が一致したか確認する

### 検証データ

今回の検証で用いたテーブルのDDLは以下のとおりです。

```sql
CREATE TABLE `orders` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `order_id` BIGINT UNSIGNED NOT NULL,
  `customer_id` BIGINT UNSIGNED NOT NULL,
  `tenant_id` BIGINT UNSIGNED NOT NULL,
  `status` ENUM('COMPLETED','PENDING','CANCELLED','SHIPPED','ORDERED') NOT NULL,
  `created_at` DATETIME NOT NULL,
  `amount` DECIMAL(10,2) NOT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uni_orderid_customerid` (`order_id`, `customer_id`)
);
```

検証データは、各シナリオに応じて自作のツールで生成しました。基本的にはシードを固定したランダムデータで、一定のルールに基づいてデータの分布を均等にしたり、意図的に偏らせたりしています。
## テストシナリオ

以下のテストシナリオを実施することとします。

1. 複合インデックスの列順
	1. Selectivity や Predicate の種類が変わっても、Index Advisor は適切な列順を選べるか
		1. tenant_idの選択性が高い: tenant数: 10,000, 各tenant: 約100行
		2. tenant_idの選択性が低い: tenant数: 10, 各tenant: 約1,000,000行
		3. created_atのRangeが狭い: 1日分だけ。 (これはクエリのWHERE句の設定)
		4. created_atのRangeが広い: 1年分。 (これはクエリのWHERE句の設定)
2. カバリングインデックス
	1. Index Advisorは検索条件だけでなく、カバリングインデックスを考慮したインデックスを推薦できるか
3. ORDER BY ... LIMIT
	1. Index Advisor は 絞り込みと並べ替えのトレードオフを正しく判断できるか

## カバリングインデックス

ここではIndex Advisorがどの程度カバリングインデックスを考慮した推薦ができるのかを確かめます。

検証SQLは以下のとおりです。

```sql
SELECT order_id, status
FROM orders
WHERE customer_id = 100;
```

この場合、カバリングインデックスの候補として `(customer_id, order_id, status)` が考えられます。ただし、場合によってはこれが常に最適であるとは言えません。

例えば、もし `customer_id` がPKまたはUKであれば、それだけで行が特定できるので、実用的には追加のインデックスは不要になりそうです。また、`customer_id, order_id, status` は明らかに `customer_id` 単体よりも長いインデックス長となるため、ストレージコストや書込み負荷の観点では不利となります。つまり、Index Advisorは読み取り性能（読み取りの見積もりコスト）のみで評価しているため、実運用では、読み取り性能以外の部分も評価すべきです。

- 期待する推薦インデックス: customer_id, order_id, status

## `ORDER BY ... LIMIT`

ここでは、`created_at`が全域で均等に分布していると仮定して、以下の２つのクエリで検証します。

```sql
SELECT id, created_at
FROM orders
WHERE tenant_id = 100
ORDER BY created_at DESC
LIMIT 20;
```

1つ目のクエリの場合、`tenant_id`を等価条件で絞り込んだうえで、その範囲を`created_at`の降順に読み取ることができるため、`(tenant_id, created_at)`は非常に適したインデックスです。

```sql
SELECT id, created_at
FROM orders
WHERE tenant_id BETWEEN 100 AND 199
ORDER BY created_at DESC
LIMIT 20;
```

２つ目のクエリの場合はどうでしょうか。インデックスにするべき列は１つ目と同様に `tenant_id` と `created_at` ですが、このクエリには絞り込みと並び替えのトレードオフがあり、どちらを前に持ってくるべきかは悩ましいです。

`(tenant_id, created_at)`の場合、`tenant_id`のRangeによって対象データを絞り込むことができます（絞り込みを優先する）。一方で、複数の`tenant_id`をまたいだ結果全体は`created_at`順には並んでいないため、`ORDER BY created_at DESC`を満たすためには、並び順に従って上位20件を選ぶ処理（`TopN`）や並び替え (`Sort`) 処理が必要になる可能性があります。

反対に`(created_at, tenant_id)`の場合、`created_at`の新しいデータから順にインデックスを読み取ることができるため、`tenant_id`の条件に一致する20件が見つかった時点で読み取りを終了できます（並び替えを優先する）。ただし、`tenant_id`による絞り込みをIndex Rangeとして利用することはできないため、条件に一致するデータが少なければ、多くのインデックスエントリを読み取る必要があります。

さらに、`tenant_id BETWEEN ? AND ?`の範囲を広げると、このトレードオフも変化します。範囲が狭い場合は`tenant_id`による絞り込みの効果が大きい一方、範囲が広くなるほどその効果は小さくなります。逆に、`created_at`を先頭にしたインデックスでは、`tenant_id`の範囲が広いほど条件に一致する行が見つかりやすくなり、`LIMIT 20`に早く到達できる可能性があります。

このような絞り込み条件の選択性と`ORDER BY ... LIMIT`のトレードオフを、Index Advisorがどのように評価するのかに注目して検証します。

### `tenant_id` を等価条件で絞り込む場合（`tenant_id = ?`）

|            | Recommended Index    | estCost     |
| ---------- | -------------------- | ----------- |
| Index無し    |                      | 22827241.94 |
| HYPO_INDEX | tenant_id,created_at | 714.10      |
| Index追加    | tenant_id,created_at | 712.05      |

このケースでは、想定通り `(tenant_id, created_at)` が推薦されました。
`tenant_id = 100` という等価条件によってインデックスのプレフィックスが固定されるため、その後ろにある `created_at` の順序をそのまま `ORDER BY created_at DESC` に利用できます。
実際の実行計画でも `(tenant_id, created_at)` に対する `IndexRangeScan` が選択され、`range:[100,100]`、`keep order:true, desc` となっています。また、`LIMIT 20` に必要な20件だけを読み取って処理を終了しており、追加の `TopN` や `Sort` もありません。

### `tenant_id` を範囲検索で絞り込む場合（`tenant_id BETWEEN ? AND ?`）

この場合、絞り込みと並び替えのトレードオフに悩んでしまいますが、サンプルクエリを素直に検証してみると、`(created_at, tenant_id)`のインデックスが推薦されます。
見積もりコストは以下の通りで、効果的なインデックスが選ばれていることがわかります。

|            | Recommended Index        | estCost     |
| ---------- | ------------------------ | ----------- |
| Index無し    |                          | 27577596.60 |
| HYPO_INDEX | created_at,tenant_id     | 6133.28     |
| Index追加    | created_at,tenant_id<br> | 6038.66     |

このケースでは `(created_at, tenant_id)` が推薦されました。
等価条件の場合とは異なり、実行計画では `tenant_id` を使った `IndexRangeScan` ではなく、`(created_at, tenant_id)` に対する `IndexFullScan` が選択されています。ただし `keep order:true, desc` となっているため、インデックスを `created_at` の新しい順に読み取ることで、追加の `TopN` や `Sort` を行わずに `ORDER BY created_at DESC` を満たしています。
このとき `tenant_id BETWEEN 100 AND 199` はインデックスの検索範囲ではなく `Selection` として評価されます。そのため、条件に一致する行を見つけるまで余分なインデックスエントリを読み取る必要があります。今回の実測では、20件を返すために992件のインデックスエントリを読み取っています。
それでも、全100万行を読み取って `TopN` を行っていたインデックス無しの場合と比べると読み取り量は大幅に減少し、実行時間も約350msから約9msまで短縮されました。
つまり、このクエリでは `tenant_id` による絞り込みを最大化することよりも、`created_at` の順序を利用して `LIMIT 20` に早く到達することのほうが有利だと判断されたことになります。

ただし、この結果から、範囲条件では常に `created_at` を先頭にすべきだとは言えません。新しいデータに対象テナントの行が少ない場合には、20件を得るまでの読み取りが増えます。今回のデータでは推薦されたインデックスによって読み取りを大きく減らせましたが、その効果は検索範囲やデータの偏りにも左右されます。

`ORDER BY ... LIMIT` を含むクエリでは、検索条件だけを見てインデックスの列順を決めることはできません。検索条件の選択性と、ソート済みのインデックスを利用してどれだけ早く `LIMIT` に到達できるかという両方を考慮する必要があります。今回の結果から、Index Advisor がこのトレードオフをコストに基づいて評価し、後者を選択できることが確認できました。

# Index Advisorを運用するときの注意点

## 推薦結果を盲信しない - Index Advisorが見落とすケース

ここでは、Index Advisorの探索範囲と限界を確認します。Index Advisorは "What-If分析" を使って探索的に最適なインデックス候補を見つけると説明しましたが、残念ながらインデックスを見つけられない場合もあります。内部ロジックで説明したように、Index Advisorはすべての複合インデックスを網羅的に評価するわけではありません。ここでは、その制約が現れる例を確認します。

## Index Advisorは読み取りコストを中心に評価する

[tenant_idの選択性が低い: tenant数: 10, 各tenant: 約1,000,000行](#tenant_idの選択性が低い%3A-tenant数%3A-10%2C-各tenant%3A-約1%2C000%2C000行) では、`(tenant_id, created_at)`が推薦されるかと予想していましたが、予想とは異なり、`tenant_id`のみの単一列インデックスが推薦されました。
直観的には、`(tenant_id, created_at)`のほうが効率的に処理されて良さそうに見えますが、ここでは、Index Advisorがどのような基準で判断しているかを改めて確認してみましょう。

`HYPO_INDEX` で、インデックス無し、`tenant_id`のみ、`tenant_id, created_at`の複合インデックスの３パターンでコストを比較したところ、`tenant_id`のみと`tenant_id, created_at`の複合インデックスではほとんど差がありませんでした。

| HYPO_INDEX | No                    | 29,768,030.09  |          |
|            | tenant_id             | 19,604,086.32  |          |
|            | tenant_id, created_at | 19,574,035.26  |          |
| インデックス追加後  | No                    | 29,910,319.66  | 385.2ms  |
|            | tenant_id             | 196,441,933.69 | 551.1ms  |
|            | tenant_id, created_at | 22,963,039.20  | 80.8ms   |

また、インデックスを追加する際には、ストレージへの影響を見逃すことは出来ません。TiDBはインデックスのキーに、対象列の値を含みます。そのため、カバリングインデックスを意識するあまり、あまりにも多くの列をインデックスに含めると、ストレージへの影響が予想以上になる場合があります。Index Advisorではそういった点に気付くことが難しいので、推薦されたインデックスの長さにも注意するようにしましょう。
## 未使用インデックスを定期的に整理する

Index Advisor は追加すべきインデックスを推薦してくれますが、削除すべきインデックスの推薦まではしてくれません。しかし、現実には使われなくなってしまったインデックスというのは、意外と隠れているものです。

ここでは、あまり使われていないインデックスを見つける方法として、`sys.schema_unused_indexes` と `INFORMATION_SCHEMA.CLUSTER_TIDB_INDEX_USAGE` をご紹介します。なお、詳細は以下の公式ドキュメントをご参照ください。
- https://docs.pingcap.com/tidb/stable/index-advisor/#remove-unused-indexes
- https://docs.pingcap.com/best-practices/index-management-best-practices/#identify-unused-indexes-using-schema_unused_indexes

### `SYS.SCHEMA_UNUSED_INDEXES` ビューを使う

`SYS.SCHEMA_UNUSED_INDEXES` は各 TiDB インスタンスの直近の起動以降に利用されていないインデックスを特定するためのビューです。

このビューの定義は以下のとおりです。見ての通り、システムテーブルを除いて、利用されていないインデックスのみを抽出しています。

https://docs.pingcap.com/tidb/stable/sys-schema-unused-indexes/#manually-create-the-schema_unused_indexes-view

```sql
CREATE DATABASE IF NOT EXISTS sys;
CREATE OR REPLACE VIEW sys.schema_unused_indexes AS
  SELECT
    table_schema as object_schema,
    table_name as object_name,
    index_name
  FROM information_schema.cluster_tidb_index_usage
  WHERE
    table_schema not in ('sys', 'mysql', 'INFORMATION_SCHEMA', 'PERFORMANCE_SCHEMA') and
    index_name != 'PRIMARY'
  GROUP BY table_schema, table_name, index_name
  HAVING
    sum(last_access_time) is null;
```

### `INFORMATION_SCHEMA.CLUSTER_TIDB_INDEX_USAGE` を使う

上記のビューはTiDBノードが起動してから未使用のものを列挙するのみですが、最終アクセス日時などを条件に抽出するなど、もう少し柔軟に検索したい場合は `INFORMATION_SCHEMA.CLUSTER_TIDB_INDEX_USAGE` を参照すると良いでしょう[^4]。

```sql
-- Find indexes that have not been accessed in the last 30 days.
SELECT
    table_schema,
    table_name,
    index_name,
    SUM(query_total) AS query_total,
    MAX(last_access_time) AS last_access_time
FROM information_schema.cluster_tidb_index_usage
WHERE table_schema NOT IN (
    'mysql',
    'sys',
    'INFORMATION_SCHEMA',
    'PERFORMANCE_SCHEMA'
)
  AND index_name <> 'PRIMARY'
GROUP BY
    table_schema,
    table_name,
    index_name
HAVING MAX(last_access_time) IS NULL
    OR MAX(last_access_time) < NOW() - INTERVAL 30 DAY;
```

その他の例としては以下のようなクエリがあります（これらのクエリを考えるにあたり、[Chat2Query](https://docs.pingcap.com/tidbcloud/ai-feature-concepts/#chat2query-preview)とChatGPTを使いました）。長いクエリとなったので、折りたたんでいます。

:::details 観測されたアクセスが100回以上あり、そのうち80%以上で対象テーブルの50%以上を読んだインデックス
```sql
SELECT
    table_schema,
    table_name,
    index_name,

    SUM(query_total) AS query_total,
    SUM(rows_access_total) AS rows_access_total,

    SUM(
        percentage_access_0
        + percentage_access_0_1
        + percentage_access_1_10
        + percentage_access_10_20
        + percentage_access_20_50
        + percentage_access_50_100
        + percentage_access_100
    ) AS bucket_total,

    SUM(
        percentage_access_50_100
        + percentage_access_100
    ) AS over_50_accesses,

    ROUND(
        100.0 * SUM(
            percentage_access_50_100
            + percentage_access_100
        )
        / NULLIF(
            SUM(
                percentage_access_0
                + percentage_access_0_1
                + percentage_access_1_10
                + percentage_access_10_20
                + percentage_access_20_50
                + percentage_access_50_100
                + percentage_access_100
            ),
            0
        ),
        2
    ) AS over_50_percent

FROM information_schema.cluster_tidb_index_usage

WHERE table_schema NOT IN (
    'mysql',
    'sys',
    'INFORMATION_SCHEMA',
    'PERFORMANCE_SCHEMA'
)

GROUP BY
    table_schema,
    table_name,
    index_name

HAVING bucket_total >= 100
   AND over_50_percent >= 80

ORDER BY
    over_50_percent DESC,
    rows_access_total DESC;
```
:::

:::details 観測されたアクセスが100回以上あり、そのうち80%以上が0行アクセスだったインデックス
```sql
SELECT
    table_schema,
    table_name,
    index_name,
    SUM(query_total) AS query_total,
    SUM(
        percentage_access_0
        + percentage_access_0_1
        + percentage_access_1_10
        + percentage_access_10_20
        + percentage_access_20_50
        + percentage_access_50_100
        + percentage_access_100
    ) AS bucket_total,
    SUM(percentage_access_0) AS zero_row_accesses,
    ROUND(
        100.0 * SUM(percentage_access_0)
        / NULLIF(
            SUM(
                percentage_access_0
                + percentage_access_0_1
                + percentage_access_1_10
                + percentage_access_10_20
                + percentage_access_20_50
                + percentage_access_50_100
                + percentage_access_100
            ),
            0
        ),
        2
    ) AS zero_row_percent,
    MAX(last_access_time) AS last_access_time
FROM information_schema.cluster_tidb_index_usage
WHERE table_schema NOT IN (
    'mysql',
    'sys',
    'INFORMATION_SCHEMA',
    'PERFORMANCE_SCHEMA'
)
GROUP BY
    table_schema,
    table_name,
    index_name
HAVING bucket_total >= 100
   AND zero_row_percent >= 80
ORDER BY
    zero_row_accesses DESC,
    zero_row_percent DESC;
```
:::

これらの利用統計を参照するうえでの注意点として、これらはTiDBノードの再起動でリセットされ、反映に最大5分の遅延があります。また、有効な統計情報があるテーブルのみが記録対象です。「30日間アクセスがない」という条件で抽出しても、十分な観測期間（TiDBノードが再起動やダウンをせずに起動し続けており、かつ有効な統計情報が保持されている状態が少なくとも30日以上続いていること）がなければ、30日間使われていないとは判断できません。

そして、削除を検討する際は、月次処理などを含む業務サイクルを確認します。公式ドキュメントでも、本番環境では対象インデックスをまず不可視にし (`ALTER TABLE t1 ALTER INDEX c1 INVISIBLE`)、業務サイクル全体への影響を観察してから削除する方法が推奨されています[^5]。

# まとめ

本記事では、TiDBのIndex Advisorの仕組みを確認し、実際にいくつかのクエリを使って、その推薦結果を検証しました。

今回の検証では、複合インデックスの列順、カバリングインデックス、`ORDER BY ... LIMIT` といったケースに対して、Index Advisorがクエリの条件やデータ分布を考慮しながら、コストに基づいて適切なインデックスを推薦できることを確認できました。特に、同じカラムを使用するクエリでも、等価条件と範囲条件で異なる列順が推薦され、それぞれ読み取り量の削減を確認できました。

一方で、Index Advisorの推薦結果をそのまま本番環境に適用すればよいわけではありません。今回の検証でも、見積もりコストと実際の実行時間が一致しないケースや、探索の過程で有効な複合インデックスが推薦されないケースがありました。また、インデックスを追加することで発生するストレージ消費や書き込み時のオーバーヘッドについても、別途考慮する必要があります。

そのため、Index Advisorは「正しいインデックスを自動的に決めてくれる機能」というよりも、「有力なインデックス候補を見つけるためのツール」と考えるのが良さそうです。

実運用では、Index Advisorによる推薦を出発点として、`HYPO_INDEX`や`EXPLAIN`で実行計画を確認し、必要に応じて実際のワークロードで効果を検証したうえでインデックスを追加します。そして追加した後も、`SYS.SCHEMA_UNUSED_INDEXES`や`INFORMATION_SCHEMA.CLUSTER_TIDB_INDEX_USAGE`を利用して継続的に利用状況を確認し、不要になったインデックスは整理していく、という運用が望ましいでしょう。

Index Advisorにインデックス設計をすべて任せるのではなく、人間が判断するための材料としてうまく活用することで、インデックス設計や日常的なチューニングの負担を減らすことができるのではないでしょうか。
