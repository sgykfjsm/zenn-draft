# この記事について

この記事ではTiDBのGenerated columnを紹介します。TiDBはMySQLとプロトコルレベルでの互換を謳っており、基本的な使い方や多くの制約は MySQL に近い一方で、実装や optimizer の振る舞いには TiDB 固有の点があります。

通常、テーブルの列はデータ型とデータ長、NULL制約などの属性を定義しますが、Generated columnは定義済みの式から導出される値を列として扱えるようにする機能です。この"定義済みの式から導出される値として扱える"という特性により、事前のETL処理によるデータ加工処理を経ることなく、加工済みの値を列として扱うことができます。あるいはアプリケーション側の処理をDBへ寄せる、といった使い方も可能です。例えば、同一テーブルのある列に`LOWER()`関数を自動的に適用したり、JSONデータから特定の要素だけをあらかじめ抽出したりといったような使い方があります。

この記事ではTiDBでのGenerated columnとは何か、どのような使い方をするべきか、Generated columnを使う上での性能やコストについてみていきます。例えば、Virtual はデータレコードに生成値を保持しない一方で、non-covering read では Stored が有利になる場面があります。本記事では、こうした違いを主に性能面から確認します。

この記事ではSQLを使った例を出していきますので、読者は基本的なSQLが理解できることが期待されますが、そうでなくてもなるべく理解できるように努めます。

## TL;DR

さきに結論を簡単にお伝えします。

- covering index前提ならVirtualは有力な候補となる
- non-covering read + 重い式ならStoredが優位になりやすい
- 差が出るかどうかは式の複雑さ・クエリ形状・index coverageに強く依存する
- 書込みの場合も含め、Virtualが常に有利とは限らない

# Generated columnとは何か

改めてGenerated columnとは何かを見ていきます。まずは以下のCREATE文を見てイメージを掴んでみましょう。

```sql
DROP TABLE IF EXISTS person;
CREATE TABLE person (
    id INT NOT NULL AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    address_info JSON,
    city VARCHAR(64) AS (address_info->>'$.city'),
    
    KEY idx_city (city)
);
```

このテーブルではJSONデータの`address_info`から`city`を抽出し、それを列として定義しています。この`city`列がGenerated columnです。また、Generated columnはインデックスにすることができます。

次に、このテーブルにレコードを新たに追加してみます。

```sql
tidb:4000 > INSERT INTO person (name, address_info) VALUES ('foo', JSON_OBJECT('city', 'tokyo'));
Query OK, 1 row affected (0.02 sec)

tidb:4000 > SELECT * FROM person;
+----+------+-------------------+-------+
| id | name | address_info      | city  |
+----+------+-------------------+-------+
|  1 | foo  | {"city": "tokyo"} | tokyo |
+----+------+-------------------+-------+
1 row in set (0.00 sec)
```

`city`列に事前に定義された計算式に従った結果が出力されました。

このように、Generated columnとは、定義済みの式から導出される値を列として扱えるようにする機能です。個人的な印象ですが、ETL処理でおこなう加工をDB側に寄せるような使い方、あるいは逆に予想される使い方を先回りして事前計算するような使い方が多いような印象です。

なお、同一テーブルの列を参照する式だけではなく、例えば`1+2`のような定数式に近い形を定義することも可能で、`RAND`、`UUID`、あるいは `CURRENT_TIMESTAMP`といったnon-deterministicな関数は設定できません。詳細は以下のリンク先をご確認ください。

- https://docs.pingcap.com/tidb/stable/generated-columns/#limitations

次にもう少し、Generated columnの特性を見てみましょう。

`INSERT`や`UPDATE`でGenerated columnに値を追加したり更新することはできません。

```sql
tidb:4000 > INSERT INTO person (name, city) VALUES ('bar', 'osaka');
ERROR 3105 (HY000): The value specified for generated column 'city' in table 'person' is not allowed.

tidb:4000 > UPDATE person SET city = 'sapporo' WHERE city = 'tokyo';
ERROR 3105 (HY000): The value specified for generated column 'city' in table 'person' is not allowed.
```

ただし、`DEFAULT`を使って暗黙的に値を代入することはできます。この説明だけだとわかりづらいので例を示します。
```sql
tidb:4000 > CREATE TABLE t (a INT DEFAULT -1, b INT AS (a+10));
Query OK, 0 rows affected (0.05 sec)

tidb:4000 > INSERT INTO t (b) VALUES (DEFAULT);
Query OK, 1 row affected (0.01 sec)

tidb:4000 > SELECT * FROM t;
+------+------+
| a    | b    |
+------+------+
|   -1 |    9 |
+------+------+
1 row in set (0.00 sec)

tidb:4000 > DROP TABLE t;
Query OK, 0 rows affected (0.13 sec)

tidb:4000 > CREATE TABLE t (a INT, b INT AS (a+10));
Query OK, 0 rows affected (0.04 sec)

tidb:4000 > INSERT INTO t (b) VALUES (DEFAULT);
Query OK, 1 row affected (0.01 sec)

tidb:4000 > SELECT * FROM t;
+------+------+
| a    | b    |
+------+------+
| NULL | NULL |
+------+------+
1 row in set (0.01 sec)

tidb:4000 > INSERT INTO t (a, b) VALUES (10, DEFAULT);
Query OK, 1 row affected (0.00 sec)

tidb:4000 > SELECT * FROM t;
+------+------+
| a    | b    |
+------+------+
| NULL | NULL |
|   10 |   20 |
+------+------+
2 rows in set (0.00 sec)
```

上記の例から、`INSERT`や`UPDATE`の場合はクエリの中でGenerated columnに値を指定するとエラーになりましたが、`DEFAULT`を指定することができるということがわかるかと思います。動作としては、Generated columnをクエリに含めない場合と同じです。ここでは文法的にこのような書き方が可能であるということを示すために紹介しました。

Generated columnは、`UUID`や`RAND`、`CURRENT_TIMESTAMP`のような、実行するたびに結果が変わるnon-deterministicな関数はサポートしていません。

```sql
tidb:4000 > ALTER TABLE person ADD COLUMN created_at_jst DATETIME AS (DATE_ADD(CURRENT_TIMESTAMP, INTERVAL 9 HOUR));
ERROR 3102 (HY000): Expression of generated column 'created_at_jst' contains a disallowed function.
```

やや制約はありますが、とくに使いづらいということもない、シンプルな機能と言えるでしょう。

## StoredとVirtual

Generated columnには`Stored`と`Virtual`の2種類があります。違いは以下のとおりです。

- Stored
	- Generated columnに計算済みの値を保存する。
	- ストレージ上に実際に値を保存する。
	- `ALTER`で追加することはできず、`CREATE TABLE`時のみに作成できる。
- Virtual
	- Generated columnには値を保存せず、参照時に値を計算して出力する。
	- ストレージに値を保存しない。
	- `ALTER`でも追加できる。

このような違いがあるため、一般にStoredのほうが読み取り性能が高い、Virtualのほうは書き込み性能が高く、ストレージ効率が良いとされています。

## VirtualとIndex

Virtualの場合、ストレージに値を保存しないと説明しましたが、実はこれは正確ではありません。TiDBではインデックスに指定されたカラムの値はTiKVのレイヤーでKey-Valueのペアに変換されます。このとき、インデックスは原則として、以下のようなフォーマットでカラムの値がマッピングされます。

```
# Primary keyまたはUnique keyの場合
Key: tablePrefix{TableID}_indexPrefixSep{IndexID}_indexedColumnsValue
Value: RowID

# Secondary indexの場合
Key: tablePrefix{TableID}_indexPrefixSep{IndexID}_indexedColumnsValue_{RowID}
Value: null
```

見ての通り、Keyにはカラムの値が含まれています。ただし、保存されるのは そのインデックスに必要な形の値であり、行データ本体の列値として保持される Stored とは意味が異なります。カバリングインデックスなどが見込める場合、Virtual generated columnを利用するのが良いと言えるでしょう。

インデックスレコードのKey-Valueのマッピングに関する詳細は以下のリンク先をご覧ください。

https://docs.pingcap.com/tidb/stable/tidb-computing/#mapping-of-indexed-data-to-key-value

## VirtualとExpression index

SQLに詳しい方であれば、Generated columnでインデックスを使えるということからExpression indexを思い出した方がいらっしゃるかもしれません。Expression indexとは以下のように、ある列に対する計算式をインデックスとして定義することです。

```sql
-- col1列の値を小文字化したものをインデックスにする
CREATE INDEX idx1 ON t1 ((LOWER(col1)));
```

Expression indexはTiDBの公式ドキュメントで"[They are implemented by creating indexes on generated virtual columns that are invisible](https://docs.pingcap.com/tidb/stable/sql-statement-create-index/#expression-index:~:text=They%20are%20implemented%20by%20creating%20indexes%20on%20generated%20virtual%20columns%20that%20are%20invisible)"と説明されており、TiDBではexpression indexは内部的にinvisibleなgenerated virtual columnを利用して実装されます。そのため、性能面や内部構造の観点では近い性質を持つと考えてよいです。  ただし、DDL・可読性・列として直接扱えるかどうかといった使用感は同一ではありません。

計算式をインデックスにしたい場合、必ずしもExpression indexを使う必要はありません。TiDB には [generated column index replacement rule](https://docs.pingcap.com/tidb/stable/generated-columns/#generated-columns-index-replacement-rule) があり、クエリ中の式がインデックスされたVirtual generated columnと厳密に一致すると、そのGenerated columnに置き換えられてインデックスが利用されることがあります。ドキュメントに記載されている例を流用します。

```sql
tidb:4000 > CREATE TABLE t(a INT);
Query OK, 0 rows affected (0.12 sec)

tidb:4000 > ALTER TABLE t ADD COLUMN b BIGINT AS (a+1) VIRTUAL;
Query OK, 0 rows affected (0.14 sec)

tidb:4000 > ALTER TABLE t ADD INDEX idx_b(b);
Query OK, 0 rows affected (0.19 sec)

tidb:4000 > DESC SELECT a+1 FROM t WHERE a+1=3;
+------------------------+---------+-----------+-------------------------+---------------------------------------------+
| id                     | estRows | task      | access object           | operator info                               |
+------------------------+---------+-----------+-------------------------+---------------------------------------------+
| IndexReader_6          | 10.00   | root      |                         | index:IndexRangeScan_5                      |
| └─IndexRangeScan_5     | 10.00   | cop[tikv] | table:t, index:idx_b(b) | range:[3,3], keep order:false, stats:pseudo |
+------------------------+---------+-----------+-------------------------+---------------------------------------------+
2 rows in set (0.00 sec)
```

上記の実行例では後から追加してインデックスにしたVirtual generated columnを参照していませんが、WHERE句の条件式 `a+1`がインデックスの式と一致したので自動的に`a+1`の部分を`b`と置き換えたような動作となりました。この置換はVirtual generated columnに対してのみ有効で、Stored generated columnには適用されません。

このように、クエリ側で式をそのまま書く使い方を想定する場合は、Virtual generated columnやexpression index のほうが扱いやすい場面があります。
# Generated columnの速度

ここからは、Generated columnのStoredとVirtualの違いを読み取りと書き込みの速度という観点で検証してみます。

今回の検証では、Generated columnに設定する計算式が軽い場合と重い場合の２パターンを試してみたいと思います。

## 検証に用いるテーブル定義

### 計算式が軽い場合

計算式が軽い場合の検証には以下のテーブル定義を利用します。

```sql
DROP TABLE IF EXISTS t_s;
CREATE TABLE t_s (
  id BIGINT PRIMARY KEY,
  i  BIGINT,
  g  BIGINT GENERATED ALWAYS AS (i+1) STORED,
  
  KEY idx_g (g)
);

DROP TABLE IF EXISTS t_v;
CREATE TABLE t_v (
  id BIGINT PRIMARY KEY,
  i  BIGINT,
  g  BIGINT GENERATED ALWAYS AS (i+1) VIRTUAL,
  
  KEY idx_g (g)
);
```

このテーブルでは、計算式の処理をできるだけ軽くし、純粋にStoredとVirtualの違いを明確にすることを目的としています。

### 計算式が重い場合

計算式が重い場合の検証には以下のテーブル定義を利用します。

```sql
DROP TABLE IF EXISTS t_json_s;
CREATE TABLE t_json_s (
  id BIGINT PRIMARY KEY,
  j  JSON NOT NULL,
  email VARCHAR(255)
    GENERATED ALWAYS AS (
      LOWER(TRIM(JSON_UNQUOTE(JSON_EXTRACT(j, '$.email'))))
    ) STORED,
  INDEX idx_email (email)
);

DROP TABLE IF EXISTS t_json_v;
CREATE TABLE t_json_v (
  id BIGINT PRIMARY KEY,
  j  JSON NOT NULL,
  email VARCHAR(255)
    GENERATED ALWAYS AS (
      LOWER(TRIM(JSON_UNQUOTE(JSON_EXTRACT(j, '$.email'))))
    ) VIRTUAL,
  INDEX idx_email (email)
);
```

このテーブルでは、計算式が軽い場合とは異なり、StoredとVirtualの違いにおいて、計算式の負荷がどの程度影響するかを確認することを目的としています。本記事では「重い式」の代表として JSON 抽出 + 文字列正規化を用いています。これは実務で比較的よくあるパターンですが、必ずしも計算コストの上限の代表例とは言えるものではありません。あくまでも現実的な運用例として設定しています。

## テストケース1: 読み取り速度の検証

基本的な方針として、covering indexが効く場合と効かない場合を試します。これは、インデックスレコードのみの参照で完結する場合とデータレコードの参照も含めることでVirtualでの計算式の処理負荷がどの程度影響するかを確認することを目的としてます。予想される結果としては以下の通りです。

- 計算式が軽い場合: StoredとVirtualに差は殆ど無い
- 計算式が重い場合: StoredのほうがVirtualよりも良い結果となる

各クエリを1,000回ほど繰り返し、レイテンシーのp50とp95を比較します。

```sql
-- covering indexが効く場合
/* stored  */ SELECT g FROM t_s WHERE g >= 1 ORDER BY g LIMIT 10000;
/* virtual */ SELECT g FROM t_v WHERE g >= 1  ORDER BY g LIMIT 10000;

-- covering indexが効かない場合
/* stored  */ SELECT i FROM t_s WHERE g >= 1 ORDER BY g LIMIT 10000;
/* virtual */ SELECT i FROM t_v WHERE g >= 1  ORDER BY g LIMIT 10000;
```

## テストケース2: 書き込み速度の検証

以下の内容で検証を実施します。
1. １トランザクションで一度に10,000レコードをインサートするクエリを、100トランザクション実行する
2. これを10回繰り返す

予想される結果は以下のとおりです。
- 計算式が軽い場合: StoredとVirtualに差は殆ど無い
- 計算式が重い場合: VirtualのほうがStoredよりも良い結果となる

最初にwarm upとして3回ベンチマーククエリを実行し、その後、各回の実行時間を計測します。

### 計算式が軽い場合

```sql
/* stored  */ INSERT INTO t_s(id, i) VALUES (1, 1), (2, 2) ... (10000, 10000);
/* virtual */ INSERT INTO t_v(id, i) VALUES (1, 1), (2, 2) ... (10000, 10000);
```

### 計算式が重い場合

テーブル `t_json_v` に対しても、対象テーブル名以外は同じ内容の INSERT を実行します。

```sql
/* stored */ INSERT INTO t_json_s(id, j) VALUES (1, 
  JSON_OBJECT(
    'email', '  User000001@Example.COM  ',
    'name',  'User 1',
    'score', 1,
    'ts',    DATE_FORMAT(
               TIMESTAMPADD(SECOND, 1, TIMESTAMP '2026-01-01 00:00:00'),
               '%Y-%m-%d %H:%i:%s'
             ),
    'active', IF(1 % 2 = 0, TRUE, FALSE)
  )
), ...;
```

### 結果

読み取りおよび書き込みの結果は以下のとおりです。参考までに最小値と平均値、最大値を記載し、計算式が軽い方を`Simple`、重い方を`Complex`としています。

検証環境に記載しておりますが、今回の検証はTiDB Cloud上で行っており、tiup playgroundとは違い、各コンポーネント間でのネットワークオーバーヘッドが測定結果に含まれています。そのため、利用したインフラの環境やリージョンなどにより、同じテストケースであっても異なる結果が出る場合があります。予めご了承ください。

上記の結果から以下を読み取ることができるかと思います。

- Simple / covering では、StoredとVirtualの差はごく小さく、p50では 0.094ms、avgでは0.731ms 程度にとどまった
- Simple / non-covering でも、StoredはVirtualよりp50で2.825ms、p95で7.209ms 速いものの、差は限定的である
- Complex / covering でも差は比較的小さく、Stored はVirtualよりp50で1.831ms、p95で3.646ms速い程度だった
- 一方で Complex / non-covering では差が明確に現れ、StoredはVirtualよりp50で16.920ms、p95で15.942ms、avgで17.173ms速い結果となった

covering indexが効いている場合、index 上に保持された値だけで完結しやすく、Virtual の再計算コストが前面に出にくいです。よって、定義済み計算式の違いや、StoredかVirtualかどうか、ということは大きく影響しないように見えます。一方で、non-coveringの場合はデータレコードへのアクセスが発生するため、Virtualでは行データをもとに生成値を評価するコストが結果に現れやすくなります。今回のComplexの結果では、JSON抽出や文字列関数のCPUコストがその差に影響した可能性があります。

このケースの結果は以下の予想をしていましたが、予想通りだったと言えるでしょう。

- 計算式が軽い場合: StoredとVirtualに差は殆ど無い
- 計算式が重い場合: StoredのほうがVirtualよりも良い結果となる
	- 特にnon-coveringでは違いが顕著となる

# 使いどころ

これまでの検証を踏まえてGenerated columnおよびExpression indexの使いどころを整理します。

## Virtual が向くケース

- covering index で完結しやすい    
- storage を増やしたくない
- SELECT でその生成値を直接返すことは少ない

## Stored が向くケース

- 生成値を列として頻繁に参照する
- generated column を通常列のように自然に扱いたい    
- non-covering read や tableアクセスが多い
- JSON 抽出や文字列加工など、式の計算コストが無視できない
- クエリから複雑な式を隠したい

## Expression index が向くケース

- 列を増やしたくない
- 特定の式にだけ index を張りたい
- クエリ側で式を書いても許容できる
- SELECT対象としてその式を多用しないか、その式を返り値として扱う必要が薄い

## 運用上の注意点

- Generated column はnon-deterministicな関数を使えない
- スキーマ変更の柔軟性は Stored / Virtual で異なる
- 複雑な式をスキーマに埋め込むと、アプリケーションの変更よりも影響範囲の把握が難しいことがある
- Expression indexは便利だが、式をクエリに繰り返し書く必要があり可読性が落ちる
- Generated column / Expression indexはoptimizerの扱いを必ず `EXPLAIN` で確認すべき
# まとめ

この記事ではGenerated columnの説明を行い、StoredとVirtualの違いを速度面で確認しました。今回の検証では、covering index が効くケースでは Stored / Virtual の差は小さい結果となりました。一方で、non-covering read かつ式の計算コストが高いケースでは Stored が明確に有利となる結果になりました。また、書き込みについても今回の結果では一貫して Virtualが有利とはならず、Generated columnの選択はwrite workloadでも単純化できないことがわかりました。したがって、Generated columnの性能差は「Stored / Virtual という分類そのもの」よりも、式の重さ・アクセスパターン・index coverageに強く依存すると考えられます。
